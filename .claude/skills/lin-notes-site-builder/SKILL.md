# Lin Notes site-building workflow

Use this skill when the user asks to build, extend, debug, deploy, or document a personal technical blog similar to Lin Notes.

## User preferences captured from this project

- The user prefers practical, staged implementation over a large rewrite.
- Keep the site static-first and Markdown-first.
- Use Decap CMS for authoring rather than building a custom admin from scratch.
- Images may be uploaded into the repository through the CMS.
- Videos should not be uploaded into the repository; use external hosting links such as Bilibili, YouTube, Cloudflare Stream, or R2 HTTPS URLs.
- PDF and Word files should be uploaded as attachments, not automatically parsed at runtime.
- DOCX conversion should be an optional local helper command that outputs Markdown for copying into the CMS.
- The user likes visible, always-accessible admin entrances for important workflows such as comment moderation.
- Before pushing, run the same checks GitHub Actions will run.
- For GitHub pushes on this machine, use proxy port `7897` when normal network access fails:
  `git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 push`

## Recommended architecture

For a similar blog, prefer this stack:

- Astro static site.
- `src/content` content collections for articles and topics.
- Decap CMS under `public/admin/` for browser-based editing.
- GitHub backend with OAuth worker for Decap login.
- GitHub Pages deployment from `main`.
- Cloudflare Worker + D1 for comments.
- Turnstile for visitor comment anti-spam.
- GitHub OAuth for comment moderation admin.
- Static JSON search index generated by Astro.
- Validation scripts that fail CI before bad content ships.

Avoid:

- Replacing Decap CMS unless the user explicitly asks for a custom backend.
- Allowing arbitrary HTML in author content.
- Uploading local video files to the repository.
- Parsing PDFs automatically into article body text.
- Bypassing checks or Git hooks.

## Content model pattern

Use structured frontmatter rather than ad-hoc Markdown conventions.

Article fields should include:

- `title`
- `description`
- `pubDate`
- `updatedDate` optional
- `tags`
- `draft`
- `featured`
- `heroImage` optional
- `attachments` optional list:
  - `title`
  - `file`
  - `type`: `pdf`, `docx`, `doc`, or `other`
  - `description` optional

Topics should be editable in Decap and select related articles by relation field rather than manually typing links.

## Decap CMS conventions

When improving the backend:

1. Edit `public/admin/config.yml` for collections, fields, hints, filters, sorting, media folders, and preview paths.
2. Put project-owned CMS customizations in `public/admin/cms-extensions.js`.
3. Load CMS extensions in `public/admin/index.html` after `decap-cms.js` and before `CMS.init()`.
4. Do not edit the bundled `public/admin/decap-cms.js` vendor file.
5. Register optional Decap editor components defensively: if an API is missing, skip without breaking CMS initialization.
6. Keep author hints in Chinese for this site.

Useful CMS features for this user:

- `publish_mode: editorial_workflow`
- `sortable_fields`
- `view_filters`
- field `hint`
- `file` widget for PDF/DOC/DOCX attachments
- `relation` widget for topic-to-post selection
- preview templates that show title, description, tags, draft state, hero image, attachments, and SEO hints

## Media rules

Use this split:

- Images: `public/images/uploads`, public path `/images/uploads`
- Attachments: `public/attachments/uploads`, public path `/attachments/uploads`
- Videos: external HTTPS links only

Validation should enforce:

- Image upload directory only allows common image formats.
- Attachment upload directory only allows PDF, DOC, DOCX.
- Block executables, archives, and local video files in upload directories.
- Markdown image paths must resolve to existing local public files unless external.
- Video links must be HTTPS and should be standalone lines in Markdown.

## Comments system pattern

For comments, keep the system lightweight:

- Visitor comment form in Astro component.
- Cloudflare Worker API handles public comment submission and admin actions.
- D1 stores comments, likes, and moderation status.
- Turnstile protects public submissions.
- GitHub OAuth protects admin moderation.
- Admin UI should show health, stats, filters, and clear moderation actions.
- Visitor UI should show success/failure states clearly.

When debugging comment submission, check:

1. Worker secrets, especially `TURNSTILE_SECRET_KEY`.
2. Frontend captures Turnstile token before re-rendering form state.
3. Worker CORS config matches the site domain.
4. D1 migrations have been applied.
5. Production Worker URL in `src/lib/site.ts` is configured.

## Domain and deployment lessons

For GitHub Pages custom domains:

- Apex/root domain should point to GitHub Pages IPs, or use provider-supported flattening.
- `www` should usually be a CNAME to the GitHub Pages host.
- If using Cloudflare as DNS, configure records in Cloudflare after setting nameservers at the registrar.
- GitHub Pages DNS errors may take time to clear after DNS changes.
- Use `nslookup <domain> 1.1.1.1` to verify public DNS.

For Workers:

- Use explicit Wrangler config paths on Windows when needed.
- Do not store secrets in the repo.
- Use `wrangler secret put` for OAuth secrets, Turnstile secret, and related values.
- Deploy Workers only when the user authorizes deployment.

## Validation workflow

Before saying a change is complete, run relevant checks from the repo root:

```bash
npm run check:media
npm run check:content
npm run check
npm run build
npm run deploy:check
```

For UI/frontend changes:

1. Start Astro dev server on a fixed port.
2. Open or request key routes.
3. Verify the golden path and a likely edge case.
4. If unable to interact with Decap login, say exactly what was and was not verified.

Useful local dev command:

```bash
npm run dev -- --host 127.0.0.1 --port 4333
```

## Commit and push workflow

Only commit and push when the user explicitly asks.

Before committing:

1. `git status --short`
2. `git diff` for relevant files
3. `git log -5 --oneline`
4. Confirm no secrets or unwanted generated files are staged.
5. Stage specific files, not `git add -A`.
6. Commit with a concise message ending with:
   `Co-Authored-By: Claude Sonnet 4.6 <noreply@anthropic.com>`

Push with proxy if needed:

```bash
git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=http://127.0.0.1:7897 push
```

## Style guidance for future site changes

- Keep the visual style calm, restrained, and engineering-focused.
- Prefer Chinese UI copy for visitor/admin-facing labels and hints.
- Preserve enough implementation detail in posts and admin guidance so the site remains a reusable engineering notebook, not just a showcase.
- Prefer small, direct changes over premature abstractions.
- Do not create large documentation sets unless the user asks; when asked, write practical maintenance docs.
